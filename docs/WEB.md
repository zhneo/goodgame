# Веб-сервис bcc spec

Сайт для аналитиков: загрузить ТЗ → агент проверяет → отчёт с пометками на полях, письмо автору, сверка с GitLab.
Вызывает **тот же конвейер**, что и CLI. Базовый `report.md` одинаков; веб может дописать служебную легенду F-ID,
сравнение прогонов и сохранённые решения ревьюера.

## Запуск

```powershell
pip install -r requirements.txt
cp .env.example .env   # вписать GEMINI_API_KEY
python -m web
```

Откройте http://localhost:8000. Сборка фронтенда не нужна: он лежит готовой статикой в `web/static/`
и отдаётся самим FastAPI. Документация API — http://localhost:8000/api/docs.

| Переменная       | Зачем                                                                 |
|------------------|-----------------------------------------------------------------------|
| `VALIDATOR_MOCK` | `1` — всегда демо-конвейер, даже если `validator/` уже есть           |
| `MOCK_DELAY`     | пауза между этапами демо-конвейера, сек (по умолчанию 0.35)           |
| `GITLAB_URL`, `GITLAB_TOKEN`, `GITLAB_PROJECTS` | подключить GitLab и проекты (`group/a,group/b`) при старте |
| `WEB_HOST`, `WEB_PORT` | адрес сервера (по умолчанию 127.0.0.1:8000)                     |
| `WEB_DATA_DIR` | каталог JSON-снимков прогонов (по умолчанию `./data/web`) |
| `WEB_STAGE_TIMEOUT` | через сколько секунд без смены этапа показать предупреждение (по умолчанию 900) |
| `LLM_ALLOWED_MODELS` | разрешённые в вебе модели через запятую |
| `APP_BASIC_AUTH` | `user:password` — вход по паролю на весь сайт и API (кроме `/healthz`). **На стенде обязателен**: без него любой, кто знает адрес, видит, меняет и удаляет все загруженные ТЗ |
| `WEB_WORKERS` | сколько проверок идёт одновременно (по умолчанию 2); остальные ждут в очереди, экран показывает позицию |

### Стенд за nginx

Готовый блок — `deploy/nginx-rr.conf`: сжатие gzip, заголовки безопасности (HSTS и др.), лимит тела 25 МБ с JSON-ответом
на слишком большой файл. В блоке `server` добавьте `server_tokens off;`. Остальные заголовки (CSP, X-Frame-Options,
nosniff, Referrer-Policy) приложение ставит само, поэтому они есть и без nginx.

## Агент и демо-режим

Агент лежит в `validator/`. Веб вызывает его через адаптер `validator/contract.py`
(`run_pipeline(doc_path, on_progress, gitlab, options)`), который запускает тот же
`validator.pipeline.run_pipeline`, что и CLI (`python main.py <вход> <отчёт.md>`), и переводит результат
в схему [web-contract.md](web-contract.md). Основное содержимое отчёта формирует тот же reporter; веб дополняет его
только служебными секциями F-ID, сравнения и решений ревьюера.

- Модель и ключ берутся из `.env` (см. `.env.example`): `LLM_PROVIDER=gemini`, `GEMINI_API_KEY`, `GEMINI_MODEL`, `LLM_FALLBACK`. По умолчанию: `gemini-3.5-flash`, затем `gemini-3.5-flash-lite` и `gemini-2.5-flash`.
- `LLM_PROVIDER=mock` — детерминированный агент без сети (для проверки интерфейса).
- `VALIDATOR_MOCK=1` — старый эвристический демо-конвейер `web/mock_pipeline.py`.
- Если выбран проект GitLab, файлы выбранных scopes выгружаются во временную папку и передаются агенту
  как контекст проекта: расхождения ТЗ с кодом попадают на вкладку «ТЗ ↔ код» со ссылкой на файл.
- Экран «Критерии» показывает ровно то, что проверяет агент (`validator/criteria.py`).

## Экраны

1. **Проверить ТЗ** — лист для drag&drop (PDF, DOCX, Markdown, TXT до 20 МиБ включительно), предпросмотр документа, проект и ветка GitLab, что сверять, критерии, модель и запуск без кэша.
   Ошибки файла: формат, размер, скан без текста, PDF с паролем, повреждённый файл, «похоже, это не ТЗ».
2. **Ревью** — 6 этапов конвейера в реальном времени, число найденных замечаний, остановка, предупреждения GitLab и лимита модели (429), повтор.
3. **Результат** — штамп вердикта, фильтры по серьёзности и критерию, текст ТЗ с подсветкой цитат и замечания на полях (клик ↔ прокрутка),
   вкладки: требования (нарезка), набор целиком, ТЗ ↔ код, трассировка, вопросы к автору, неподтверждённые выводы и паспорт; решения ревьюера и скачать `report.md`.
4. **История** — все проверки, прогресс идущих, вердикт и дефекты по серьёзности.
5. **Критерии** — каталог критериев с проверочными вопросами и шкалой серьёзности.
6. **Проекты GitLab** — подключение (URL + токен только `read_api`/`read_repository`; токен с правами записи отклоняется),
   поиск и подключение проектов, статус индексации и какие пути читает агент.

## API

| Метод | Путь | Что делает |
|---|---|---|
| POST | `/api/documents` | загрузить файл → `upload_id` и предпросмотр |
| POST | `/api/runs` | `{upload_id, title, work_type, criteria[], gitlab_project_id, ref, scopes[], model, no_cache}` → `{run_id}` |
| POST | `/api/runs/upload` | то же одним multipart-запросом (файл + поля) |
| GET | `/api/runs` | история |
| GET | `/api/runs/{id}` | статус и этап: `reading … summary`, `done`, `partial`, `error`, `cancelled` |
| GET | `/api/runs/{id}/result` | JSON результата |
| GET | `/api/runs/{id}/report.md` | тот же отчёт, что у CLI (`?download=1` — скачать файлом) |
| POST | `/api/runs/{id}/cancel`, `/retry` | остановить / запустить заново |
| POST | `/api/runs/{id}/findings/{fid}/decision` | сохранить `confirmed`, `rejected`, `duplicate` или `fixed` и комментарий |
| GET/POST/DELETE | `/api/gitlab/connections` | подключения GitLab |
| GET | `/api/gitlab/connections/{id}/projects?search=` | проекты, доступные токену |
| GET/POST/DELETE | `/api/gitlab/projects`, `/{id}/sync`, `/{id}/branches` | подключённые проекты |

Запуски и результаты атомарно сохраняются на диск; незавершённый при рестарте прогон отмечается ошибкой. Загруженный исходник может быть недоступен для повтора после рестарта. Токены GitLab и ключи LLM не попадают во фронтенд.

Замечания без подтверждённой цитаты показываются отдельно и не влияют на сводку, вопросы и вердикт.
